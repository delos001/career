# Inventory Builder — Quality Checks

Cumulative quality checks from manual reconciliation passes of `personal/profile/inventory.md`. The `inventory` builder skill must encode these so future creation and refresh do not require manual reconciliation. Each check is a defect class observed during review; checks new to this file should be added inline as future reconciliation surfaces them.

## Finding Resolution Protocol

User decisions on findings are authoritative; the builder applies the response. The post-resolution state must satisfy the corresponding rule-file definition (substantiating Description vocabulary for tag fields per `rules/orientations/*.md` and `rules/specialties/*.md`; Impact value-type matching realized outcome). If the user retains a tag, sharpen Description to substantiate; if the user changes the tag, verify the new tag is substantiated.

If neither sharpening nor retagging produces a substantiated state, escalate as a taxonomy-coverage gap: evaluate whether a new orientation/specialty is needed or whether the existing rule file's vocabulary should extend to cover. Do not force-fit. Same logic as the catch-all escalation rule for Specialty in §2.

Applies at creation, refresh, and audit.

## Audit Phase Ordering

Substantive-change phases (those that add, split, modify, retag, or delete entries) execute BEFORE verification phases. Verification phases run last so they cover the post-change state, including all entries newly created or modified during the substantive-change phases. This minimizes rework where a verification phase would otherwise miss defects in entries created later in the audit.

**Substantive-change phases:** coverage (per-RL density gaps surfacing leadership-coverage additions and pattern-of-work framing; atomic decomposition of bundled umbrellas; description-scope completeness fixes), taxonomic (specialty/orientation boundary verification, catch-all escalation, retags).

**Verification phases:** structural integrity (§1), content quality within entries (§2), cross-entry quality (§3), voice consistency (§4).

**Application:** for any entry created or modified during a substantive-change phase, the entry passes through the verification phases before audit close. Builder records the change-set during substantive phases and runs the verification pass against the change-set (or against the full inventory if cheaper). When sequencing is reversed (verification first, then substantive), schedule a verification re-run on the change-set before closing the audit.

## 1. Structural Integrity

- **PR Industry uses `independent`.** Independent / volunteer projects tag `Industry: independent`, not an industry-pack value (employer sector framing does not apply). Validation on PR-prefixed entries.
- **Empty optional fields render cleared.** `Last Used:` and similar render with no value, not `N/A` / `null` / placeholder text.
- **Type field is controlled vocabulary.** Enum: `{Direct, Contract, Freelance, Military}`.
- **Allocation field is required on every RL record.** Section 7 RL records carry an `Allocation: <percentage>%` line capturing fraction of one FTE on this role at the role's most current (steady-state) value, not initial or weighted-average. Default for full-time roles: `100%`. Partial roles carry user-provided value (e.g., `20%` for a 20%-time concurrent assignment). Cross-employer overlapping roles (primary + freelance) are not constrained to sum to 100%; freelance time is additive on top of primary. Stacked same-employer roles (concurrent layered titles at the same company) report each role's allocation just before transition or end, not the historical split during overlap. Required field, present on Background Roles for schema consistency. 2026-05-08 reconciliation: field added to all 20 RL records; partial-allocation values: RL-008 (20%), RL-012 (20%), RL-013 (80%), RL-016 (10%); all others 100%.
- **Atomic inventory: one entry per role-context.** A task performed under multiple RLs creates a separate EX entry per RL. Dedup logic scopes within-RL only; cross-RL identical descriptions are intentional, not redundancy.
- **Single Impact line per entry.** Each EX/PR entry has at most one `Impact:` line. Two `Impact:` lines (typically flanking `Context:`) is a residual from edit cycles and a structural defect. Builder validates at audit time. 2026-05-06 reconciliation: EX-184 had two Impact lines after a prior content-merge edit; second deleted.
- **Every entry has an Impact line.** Each EX/PR entry must have exactly one `Impact:` line. Missing-entirely is a structural defect distinct from "two Impact lines"; bare-tag form (`Impact: <value-type>` with no body) is acceptable per the bare-tag Impact convention, but total absence is not. 2026-05-07 reconciliation: 38 entries (mostly older RL-003/005/006/007/010 roles plus a few RL-014/015/016) had no Impact line; bulk-resolved with user-provided activity-outcome notes producing 38 inserted Impact lines and 9 updated bare-tag lines (47 total).

## 2. Content Quality Within Entries

- **Tense uniformly past.** Lead verb is past tense across all Description fields.
- **No unsupported quantification.** Numeric claims (dollars, percentages, counts, headcount) require user-provided substantiation; otherwise dropped, not estimated. Builder surfaces each numeric claim for verification at build.
- **No fluff phrasing.** Qualifier-heavy phrasing ("successfully delivered", "leveraged best-in-class", "spearheaded transformative") requires concrete substance behind it or gets cut.
- **Readability pass at draft.** Awkward sentence construction is rewritten at draft, not deferred to reconciliation.
- **Description excludes purpose-clause leakage.** Patterns to detect at audit: trailing "to [verb]…" clauses stating *why the work was done* rather than *what the activity was*; "so [outcome] would not recur" framings; date-anchor clauses ("beginning in [year]") that establish temporal positioning. Move purpose to Impact (when realized outcome present) or Context (when situational positioning), or drop entirely if the value-type tag already conveys the intent. **Borderline distinction:** "to [verb]…" that anchors what the *activity itself* did (e.g., "Developed dashboards to monitor X") is acceptable scope-anchoring; "to [verb]…" that anchors *why the work was done* (e.g., "developed scripts to enhance compliance monitoring") is purpose-clause leakage. 2026-05-06 reconciliation: EX-024 (date anchor moved to Context), EX-064 (philosophy framing moved to Context, activity surfaced from Context to Description), EX-096 (goal clause stripped, Impact already carried realized outcomes), EX-149 (purpose clause stripped, substantive Impact added), EX-168 ("so the same gap would not recur" stripped).
- **Forward-looking framing does not substantiate present-work specialty tags.** Phrases like "aligned to future AI-enabled automation goals" do not substantiate an `ai-engineering` tag. Tags reflect work *performed*, not work *prepared for*. Same logic applies to other forward-looking phrasings ("positioned for…", "prepared the foundation for…"). Builder applies bare-tag-substantiation rule against forward-looking phrases by treating them as non-substantiating. 2026-05-06 reconciliation: EX-137 retagged from `ai-engineering` to `data-engineering | quality-compliance` — the digitization/metadata foundation work was DE/QC-shaped, with AI mentioned only as a forward-looking aspiration.
- **No parent-domain catch-all on Specialty tags; catch-all situations trigger taxonomy review.** Specialty tag substantiates from work *content* (what was done, what was trained on, what was authored), not from the role's parent domain. Common defect: tagging a training entry with the role's parent specialty (e.g., `clinical-operations`) when the trained content was a tool, technology, or method belonging to a different specialty. **Escalation trigger:** when tagging produces a situation where only "catch-all" or "closest-match" tagging is feasible (no existing specialty's Capability vocabulary, Terminology, Knowledge-transfer mode, or Adjacency cleanly substantiates the work), do not force-fit the closest tag. Stop and evaluate: (a) does a new specialty need to be added; (b) does an existing specialty's Capability vocabulary or Terminology need to be extended to cover this work shape; (c) does an adjacency relationship need to be added or strengthened. Forced catch-all tagging hides taxonomy gaps from the rule files where they belong; surfacing them keeps the rule files as the single source of truth for substantiation. Per `specialty-axis-training-as-specialty-work-2026-05` + `specialty-training-entries-catch-all-cleanup-2026-05` (7 EX entries retagged 2026-05-06: EX-183, EX-185, EX-188, EX-189, EX-199, EX-200, EX-201). 2026-05-07 broader audit (closes `inventory-broader-catch-all-audit`): ~70 multi-specialty entries reviewed across 9 co-tag clusters; 21 retag actions applied (16 dropped clinical-operations as parent-domain catch-all where work content didn't substantiate; 3 added missing tags including quality-compliance on EX-162/EX-176 and people-leadership on EX-146; 2 entries got Description scope expansion per the new "Description scope completeness" rule). 1 entry deleted (EX-112: ambiguous R-script-templates entry not load-bearing). clinical-operations tag count went 170→151. **Distinguishing substantiated co-tag from parent-domain catch-all:** clinical-operations substantiates when work content references study lifecycle activities (monitoring, protocol management, sponsor coordination, regulatory work, GCP, ICH), clinical-trial-specific frameworks (RBM, KRI, CSM, CDISC SDTM/CDASH, IMWG, Part 11), or clinical-research data domain expertise (CRA training, site management, EDC/CTMS/IXRS as venue plus content); clinical-operations does NOT substantiate when only role context is clinical-research and activity is pure data-engineering/data-science/operations-strategy/people-leadership.

## 3. Cross-Entry Quality

- **Redundancy detection scoped within-RL only.** Within a single RL, no two entries describe substantially the same work. Identical descriptions across different RLs are preserved per atomic inventory.
- **Coverage entries protected from redundancy collapse.** Entries created to fill a coverage-completeness gap (leadership-coverage prompts per §5; pattern-of-work declarations; concurrent-role drift recovery; any entry surfaced by a Phase 5 coverage check) carry implicit coverage provenance. Cleanup passes must not collapse such entries on within-RL similarity grounds unless the coverage dimension they fill is genuinely duplicated by another retained entry. Builder validates: before deleting any entry as "redundant," confirm (a) which coverage dimension(s) it fills, and (b) that another retained entry covers the same dimension with equivalent specificity. **Distinguishing genuine redundancy from coverage overlap:** two entries describing the same activity at the same altitude/stage/layer are redundant; two entries each filling a distinct leadership-coverage dimension (e.g., people management vs escalation handling) are not redundant even when both reside in the same role's leadership-tag cluster. 2026-05-08 reconciliation: 9 RL-011 leadership-coverage entries (EX-202 through EX-210 at commit `24def9d`) deleted at commit `c2b6d96` ("cleaned up redudantn and overlapping EX entries") were verified non-redundant against retained 8 entries on every covered dimension (people management, escalation handling, sponsor/PI communication, approval/review work, cross-functional coordination); restored from commit `24def9d` and renumbered where needed to avoid ID collisions (people management → EX-211; escalation point → EX-212; investigator meeting content → EX-213; remaining 6 retained original IDs EX-203, EX-206-210). Cleanup pass had collapsed coverage entries on lead-verb similarity (multiple "Reviewed and approved" entries) without verifying the underlying activities were distinct.
- **ID immutability after creation; deleted IDs retire, not recycle.** Once an EX or PR ID is assigned to an entry, it does not get reused for unrelated work even after the original entry is deleted. Recycling deleted IDs onto new entries makes git-history-based recovery unsafe (restoration creates ID collisions when the recycled ID has been reassigned). Builder allocates new IDs from `max(existing) + 1` regardless of gaps from deletions. Per audit-time check: recycled-ID detection compares ID-to-content stability across commits; flag any ID whose Description shifts to a substantively different activity. 2026-05-08 reconciliation: cleanup at commit `c2b6d96` deleted RL-011 EX-202/204/205 and recycled those IDs onto new RL-020 entries (capability architecture, EDC API validation, AI agent evaluation); when restoring the deleted RL-011 work, IDs collided with the live RL-020 entries — restoration required renumbering RL-011 entries to EX-211/212/213 to preserve the live RL-020 IDs.
- **Impact ≠ Description restated.** The Impact line carries only what is beyond the Description. Strip from Impact (not outcomes): audit/diagnostic findings (move to Description or Context), pattern descriptions (Context), qualifier clauses (Context), mechanism narratives (Description), purpose/aspirational framing (drop; value-type tag carries it), attribution caveats (Context).
- **Impact has multiple legitimate forms.** Quantified outcome; bounded qualitative outcome; or strategy/research/roadmap impact (alignment, decision enablement, optionality created, risk surfaced, knowledge produced). Production deployment is not required for Impact to be present.
- **Context trimmed to CV altitude.** Cut mechanics (step/person/function counts when generic descriptors suffice), colorisms restating plain claims, implementation tactics, and designer-decision defenses. Keep prior state, constraint envelope (resource model, headcount, organizational positioning), and load-bearing scope bounds.
- **Bare-tag Impact: substantiate or keep bare.** An entry with `Impact: <value-type>` and no body must either gain a substantiating body at build time or stay bare. Dropping the Impact line entirely is not the convention. Builder flags bare-tag Impact for user resolution.
- **Multi-value-type Impact prefix permitted.** Impact value-type prefix may be a single value or comma-delimited list (e.g., `Impact: Capability Building, Quality Improvement, Risk Reduction` or `Impact: Capability Building, Risk Reduction: <prose>`). Multi-value reflects work that produces value across multiple types. Per `impact-field-semantics-2026-05`.
- **Value-type accuracy review at audit time.** Verify each Impact's value-type prefix matches the realized outcome shape described in the prose body. Common gap: `Scalability/Growth Enablement` is undercounted because work-state `greenfield`/`scaling` captures situational frame, not realized outcome. Builder scans Description/Context/Impact for scope-expansion, library-reusability, org-capacity, capability-infrastructure, and growth-readiness language; flags entries where SGE outcome is implied in prose but not represented in the value-type prefix. Note: work-state and value-type are distinct axes (situational vs realized-outcome); presence of one does not imply the other. 2026-05-07 reconciliation: 14 entries augmented with SGE (EX-044, EX-095, EX-124, EX-125, EX-126, EX-127, EX-128, EX-132, EX-152, EX-157, EX-160, EX-165, EX-171, EX-172); SGE count went 4→18.
- **Restructure license at audit time.** Status-reached outcomes mistakenly placed in Description (e.g., "Developed roadmaps that shaped functional priorities") move to Impact during reconciliation. Activity verbs and methodology stay in Description; realized outcomes move to Impact. Same applies to outcomes mistakenly placed in Context — move to Impact when they describe a status reached, not a situational frame.
- **Per-RL completeness.** Every RL in Section 7 must produce at least one retrieved entry in any generated CV, **except RLs explicitly listed in the "Background Roles (Not Tagged)" section** which are intentionally excluded from tag extraction (career-continuity coverage only; no EX entries expected). Dropped tagged roles read as employment gaps regardless of retrieval-relevance score. cv_targeted enforces minimum-one-per-RL on tagged RLs only; if retrieval surfaces no leadership-translatable bullets, include 1-2 bullets minimum framed as scope/context. Concurrent roles fold under one company header with title concatenation ("Title A / Title B (concurrent)"). "Earlier Professional Roles" section acceptable for older roles, but must list each role with company and dates. Apply at draft time, not post-hoc. 2026-05-07 audit: RL-001 (Medic), RL-002 (Phlebotomy Technician), RL-004 (Pharmacy Technician) confirmed as Background Roles, zero-entry by design.
- **Concurrent-role tag drift.** When a role is concurrent with another role at the same employer, work specific to the concurrent role tends to drift into entries tagged to the primary role. Builder must check zero-entry RLs against entries tagged to concurrent peers for drift candidates (e.g., Infosario Business Champion work tagged to the concurrent Process Technology Specialist role). 2026-05-04 reconciliation: RL-008 had zero entries; relevant work was tagged to concurrent RL-009.
- **Bare-tag substantiation extends to tag fields.** Specialty and Orientation tags require substantiating language in the Description that maps to the corresponding rule file vocabulary (`rules/specialties/*.md`, `rules/orientations/*.md`). Bare tag = sharpen Description or drop tag. Same logic as bare-tag Impact applied to tag fields. 2026-05-05 reconciliation: PR-001 and PR-005 had `data-engineering` tag with no DE-vocabulary in Description; tag dropped after creating a separate DE-substantiated entry (PR-003) that absorbed the schema/relational-model/document-loading work.
- **Multi-value Orientation per `inventory-entry-multi-value-orientation-2026-05`.** Orientation may be single-value or pipe-delimited dual-value with primary/secondary asymmetry (`Orientation: <primary> | <secondary>`). Each value must independently substantiate per `rules/orientations/<value>.md`; un-substantiated values get dropped. Discipline: dual-tag only when work substantively carries both shapes, not as a hedge against tag ambiguity. Each tag is an independent supplemental tag-pull trigger at retrieval, so single-tagging dual-shape work creates retrieval false negatives. **Common dual-shape patterns:** "Built X capability/library + standardize repeatable mapping" → `transformation-strategy | process-operations`; "Built X platform/site + governance organization" → `platform-technology | process-operations`; "Redesigned and operationalized X process around standardization principle" → `transformation-strategy | process-operations`. 2026-05-08 prior-cluster force-pick re-audit (closes deferral `inventory-prior-cluster-force-picks-multi-orientation-reaudit`): 7 entries dual-tagged across RL-019/020 BioMarin cluster — EX-128 (Championed integration), EX-126 (DTA library + lab-specific configuration), EX-125 (test mapping library + cross-study terminology), EX-127 (conformance check library + domain-specific design), EX-124 (DTA process redesign + standards/SOPs), EX-044 (LLX onboarding + capability construction), EX-159 (SharePoint build + governance organization).
- **Integration framing for umbrella Impact.** When an umbrella entry's Impact references named sub-initiatives that have their own EX entries, frame the umbrella as the integration framework binding otherwise-separate workstreams; avoid wording that reads as claiming the listed initiatives. Reduces rollup-credit-taking risk. 2026-05-05 reconciliation: EX-157 reworded from "Operating model converged a portfolio of distinct initiatives (...)" to "Operating model functioned as the integration framework binding otherwise-separate workstreams (...)".
- **Activity-verb dedup across paired entries.** Two entries on the same body of work cannot both lead with the same activity verb. Reframe one entry to specify a distinctive output. 2026-05-05 reconciliation: EX-101 and EX-152 both led with "Designed workflows and led automation development"; EX-101 reframed to dashboards-built-on-platform, leaving platform-build entirely with EX-152.
- **IC vs leadership co-existence requires clean activity boundary.** When a single role had both directorial and IC contributions on the same workstream, two entries can coexist with sharp verb separation: directorial entry uses verbs like directed, oversaw, governed; IC entry uses personally contributed, authored, performed. IC entries drop accountability and ownership framing (those belong to the directorial entry). Outcome attribution on IC entries scopes only to personally-executed work, not portfolio-level. 2026-05-05 reconciliation: EX-138 narrowed to IC contribution after EX-139 retained directorial framing on the same EDC build workstream.
- **Multi-position differentiation (altitude, stage, layer).** When two entries at the same RL describe the same domain (e.g., vendor management, lab data acquisition, data review) but operate at different positions along an altitude axis (strategic vs operational/tactical), workflow stage axis (governance/setup vs execution; build vs adoption), or layer axis (oversight vs hands-on; sponsor-side vs CRO-side), Description vocabulary must explicitly signal the position. Implicit positioning (different lead verbs alone, or tag differences alone) is insufficient when domain words overlap; auditors will re-flag as duplicate. Surface explicit position vocabulary in the Description: tactical/operational entries use cadence, run-rate, weekly priorities, issue resolution, execution risk; strategic entries use alignment, scope decisions, prioritization, capability investment, governance; stage entries name the stage (post-DTA execution, pre-deployment governance, pilot phase); layer entries name the layer (sponsor-side oversight, hands-on review, CRO-side execution). 2026-05-07 reconciliation precedents: EX-050 / EX-052 (RL-018, vendor direction altitude — operational vs strategic); EX-054 / EX-055 (RL-017, lab data lifecycle stage — post-DTA execution vs DTA governance); EX-001 / EX-002 (RL-010, data review layer — sponsor-side CRO oversight vs hands-on data review). All three pairs were re-flagged across multiple audit cycles before explicit position vocabulary was added; sharpening prevented re-flagging.
- **Parallel-activity tag consistency.** When two entries describe parallel work on the same platform/system/team/program within the same role, their Specialty tags should match unless the work is genuinely distinct. Cross-entry tag-set comparison at audit time. 2026-05-06 reconciliation: EX-060 and EX-061 (both advisory work on the same Elluminate RBM platform at eClinical, RL-016) had divergent Specialty tags (`clinical-operations | data-engineering` vs `clinical-operations`); reconciled to match by dropping the unsupported `data-engineering` from EX-060.
- **Concurrent flag bilateral consistency in Section 7.** When two roles in Section 7 have overlapping date ranges of at least 2 months, both must carry `Concurrent: Yes`. Asymmetric flag pairs (one Yes, one No) are defects. **Strict overlap definition:** boundary-month transitions (RL-A ends month X, RL-B starts month X) are sequential, not concurrent; only ≥2-month shared spans count. Builder cross-validates flag pairs against date ranges at audit time, and where a double-No overlap is detected, surfaces the date-correction-vs-flag-flip choice to the user (data error and genuine concurrency are both plausible). 2026-05-06 reconciliation: RL-017 marked `Concurrent: No` despite ~2-month overlap with RL-016 (`Yes`); RL-017 corrected to `Yes`. 2026-05-07 reconciliation: 8-month phantom overlap between RL-004 (Pharmacy Technician) and RL-003 (Clinical Research Technician) resolved by date correction (RL-004 Start Date 2006-01 → 2007-01); Background Roles year-range updated to match. Note: the Concurrent flag is a deliberate signal to CV reviewers that overlapping dates are intentional concurrent roles, not data errors or role-hopping; consistency is essential for the signal to remain credible.
- **Operational-role accountability outcome convention.** For CTM, CDM, and operational accountability entries lacking quantified or strategy-shaped Impact substance, a consistent bounded qualitative outcome pattern is acceptable: "data collected, cleaned, analyzed, submitted on time across [scope]; audit-ready posture maintained." This passes the bounded-qualitative-outcome test from the Impact-form rule. Reuse of this pattern across multiple operational-accountability entries is intentional convention, not redundancy. Builder may auto-apply when the entry's Description matches the operational-accountability pattern and the user confirms no entry-specific outcome substance is available. 2026-05-06 reconciliation: EX-088, EX-083, EX-089, EX-052, EX-176, EX-054, EX-055, EX-056, EX-057, EX-058 adopted this pattern across RL-013 / RL-018 / RL-017 / RL-011 / RL-010.

## 4. Voice Consistency

- **Lead-verb agency matches Level.** Leadership-level entries do not lead with hedging verbs (assisted, supported, participated in, contributed to). IC-level entries do not lead with claim-strong verbs (spearheaded, championed, pioneered) unless underlying work supports it. Builder validates lead-verb category against the Level field.
- **Implicit third-person, no first-person.** No "I", "we", "the team and I". Implicit subject + past-tense verb.
- **No em-dashes in prose fields; en-dashes normalized to hyphens.** Em-dash (—) prohibited in Description, Impact, Context. Aligns with global writing-style rule and CV format-spec rule (`cv-format-spec-from-axes`). Replacement principles when fixing existing content: clause-attaching connectors → comma; appositive expansions → colon; standalone clauses with semantic break → semicolon or period; parenthetical asides → parentheses. **En-dash (–) also normalized to hyphen (-) file-wide** for stylistic consistency on number and year ranges (e.g., "8-12 sites", "2017-2019"); avoids ambiguity in viewers that render Unicode dashes inconsistently. 2026-05-07 reconciliation: 10 en-dashes replaced with hyphens (5 in prose fields on number ranges; 3 in Background Roles year ranges; 2 in §10 academic year ranges).
- **Bold on Description only.** Description value wrapped in `**...**`; no other field bolded.
- **Parallel construction within (RL, primary Orientation) bucket.** Entries that share an RL and a primary Orientation value follow roughly parallel verb → object → modifier shape. Outliers flagged. Scope matches the Section 8 within-RL ordering bucket per `inventory-section-8-rl-grouping-2026-05` (replaces the prior topical-sub-section scope).
- **Level field aligns to Description's lead-verb character (extends the Lead-verb agency rule).** Hands-on IC verbs (developed, performed, validated, identified, conducted, designed, compared, implemented) → `Level: ic`, regardless of role title. Leadership verbs (directed, governed, oversaw, championed, established, led — when scope is org-level) → `Level: leadership`. Mismatch resolution paths at audit: (a) **change Level to match the verb** when the activity scope is genuinely IC even though the role title is senior; (b) **change the verb to a leadership-coded equivalent** when the activity scope is genuinely leadership-shape (e.g., system-level Part 11 oversight across vendors and platforms) but the verb under-codes the level. Path (a) preferred for hands-on technical work in senior roles (IC technical contribution within a leadership role co-exists per the IC-vs-leadership co-existence rule). Path (b) preferred when the work IS leadership-scope and only the verb was mis-coded. 2026-05-06 reconciliation, path (a): EX-138, EX-053, EX-099, EX-198 changed from `leadership` to `ic` (hands-on activity inside leadership roles). Path (b): EX-130, EX-131, EX-193 verb changed from "Performed" to "Oversaw"/"Directed" to match leadership-scope Part 11 oversight. 2026-05-08 reconciliation, path (b) compound chains for end-to-end-led initiatives: EX-137 "Digitized" → "Designed, digitized, and operationalized"; EX-216 "Mapped" → "Designed, mapped, and operationalized"; EX-213 "Developed and presented" → "Co-authored, reviewed, and delivered" (chain capturing partial-authorship + review/edit + delivery for non-end-to-end leadership work). Compound chains acceptable at leadership level when at least one verb in the chain is leadership-coded (typically the closing verb: operationalized, established, delivered, governed).
- **No line-management framing implication.** Per the user's clarified background, all leadership experience is operational management of operational teams in matrix environments; there is no direct line-management experience. Builder must avoid framings that imply line management: (a) **verb "Managed" applied directly to people/teams** in operational-matrix contexts (use "Operationally led" / "Directed" instead); (b) **phrases like "held accountability for individual performance"** that imply performance management of direct reports (use "operational accountability for team delivery" or similar); (c) **"without holding direct line management" framing** as a position-vocabulary signal (implies the contrast exists somewhere in the user's history; it does not, and the framing is itself misleading). Distinguishing axis at audit: line-management vs matrix-management is NOT a valid position-vocabulary axis for this user; multi-position differentiation should use scope axes (build vs execution; strategic vs operational; sponsor-side vs CRO-side) instead. 2026-05-08 reconciliation: EX-211 "Managed a regional team... held accountability for individual and collective team performance" → "Operationally led a regional team... held operational accountability for team delivery"; EX-219 reframed end-to-end after "matrix oversight... without holding direct line management" framing was identified as latently overlapping with EX-139 build oversight (the false line-mgmt-vs-matrix axis disappeared when work was reframed on workflow-stage axis: build vs run-state); EX-166 "Provided informal direct management support" → "Provided performance feedback and career development coaching".

## 5. Coverage

- **Per-RL entry count proportional to role depth.** Each RL's entry count and content scope are proportional to tenure, scope, and seniority. Builder reports per-RL entry count + content-scope summary at build/refresh; flags outliers (sparse long roles, dense short roles). **Density math uses allocation-adjusted FTE-months as the denominator:** `effective FTE-months = tenure-months × (Allocation / 100)`; entries-per-FTE-month = entry-count / effective FTE-months. A 22-month role at 20% allocation is 4.4 effective FTE-months, so 6 entries at that role is 1.36 e/FTE-mo (normal density), not 0.27 e/mo (apparent sparseness). Builder applies allocation adjustment automatically when computing density outliers; raw tenure-months is reported alongside for reference but not used for outlier detection. 2026-05-08 reconciliation: RL-012 (CSM Deployment Lead, 22 mo × 20% = 4.4 effective FTE-mo, 6 entries → 1.36 e/FTE-mo), RL-008 (Infosario Business Champion, 23 mo × 20% = 4.6, 4 entries → 0.87), and RL-016 (RBM Software Consultant freelance, 9 mo × 10% = 0.9, 2 entries → 2.22) all flagged sparse on raw-tenure math but normal/dense on allocation-adjusted math; PASS-as-explained. **Background-role exemption:** RL records carrying `Experience Entries: None` (Section 7) are exempt from this check; zero EX entries is the expected state, not a sparse-role defect. Implements the prior "Background Roles exception to per-RL completeness rule" per `inventory-section-8-rl-grouping-2026-05`.
- **Recall-horizon discount for older roles.** Roles ending >15 years before audit time carry naturally lower recall fidelity than recent roles; entry-count expectations scale to recallable scope, not full tenure-months. Compounds with role-shape: early-career repetitive-technician work (specimen collection across hundreds of patients, follow-up across multiple trials) legitimately concentrates into a smaller number of pattern-shape entries than later-career project-based work where each project is recall-distinct. Builder applies recall-horizon discount when flagging sparse outliers; raw FTE-month density is reported alongside but not used for outlier detection on roles >15 years old. 2026-05-08 reconciliation: RL-003 (Clinical Research Technician @ DCRI, 2002-08 to 2006-08, ended ~20 years before audit, 5 entries) flagged sparse on raw FTE-month math (0.10 e/FTE-mo) but PASS-as-explained on recall-horizon + repetitive-technician-work grounds.
- **Atomic decomposition of bundled umbrella entries.** When an umbrella entry packs multiple distinct activities into one Description (e.g., "led adoption through training, consultation, and liaison"), builder flags for decomposition into one entry per activity. Umbrella role-framing belongs in Context of one of the atomic entries, not as its own bundling Description. 2026-05-04 reconciliation: EX-155 ("Served as Business Champion: led adoption through training, end-user consultation, and liaison") decomposed into 4 atomic entries (create+deliver, support-architecture training, surfacing at meetings, feedback loop). **Hollow scope-language exception:** when a candidate atomic entry's Description claims oversight/planning of activities ("oversaw X, Y, Z planning") with no concrete artifact at handoff, it collapses (delete) rather than decomposes. 2026-05-05 reconciliation: EX-206 ("oversaw delivered-capability validation, user adoption, and knowledge institutionalization planning") deleted after concrete-artifact test confirmed no written artifacts existed.
- **Tighten-vs-decompose decision tree for umbrella candidates.** Not every colon-list Description is a decomposable bundle. Builder applies these distinctions before triggering atomic decomposition: **(a) Workflow / lifecycle umbrellas → TIGHTEN.** When the colon-list items are sequential phases of one workflow (configure → review → deploy → tune → document) or lifecycle stages of one role (hire → train → manage → close), they are not separable activities. Tighten by moving mechanism narrative to Context; preserve the unifying activity in Description. **(b) Integration-framework umbrellas → PASS.** When the umbrella binds otherwise-separate workstreams that have their own EX entries, the umbrella's value IS the integration framing (per the integration-framing rule in §3). Don't decompose; keep umbrella role-framing in Description, integration framing in Impact. **(c) Separable-deliverables umbrellas → DECOMPOSE.** When the colon-list items are parallel deliverables of one initiative (each with distinct stakeholders, distinct artifacts, distinct retrieval value), decompose into atomic entries; umbrella role-framing moves to Context of one atom. **(d) Scope/format detail with colon → PASS (false positive).** When the colon-list is scope qualifier (formats, audiences, content areas, oversight domains) rather than activities, the colon-list-detector fired on a structural pattern that doesn't match the rule semantics. 2026-05-08 reconciliation: applied this distinction across 19 umbrella candidates: TIGHTEN — EX-080 (CSM optimization workflow), EX-172 (internship lifecycle), EX-184 (CSM change-management lifecycle), EX-121 (reporting portfolio governance), EX-137 (DM planning digitization stack); DECOMPOSE — EX-132 (DQS planning redesign with separable deliverables → EX-214/215/216); PASS via integration-framework — EX-157 (external data acquisition operating model); PASS via false-positive — EX-001, EX-033, EX-050, EX-055, EX-060, EX-061, EX-088, EX-090, EX-097, EX-185 (scope/format detail mistaken for activity bundle).
- **Description scope completeness — opposite of atomic decomposition.** When the actual work involved multiple concurrent or sequential sub-activities (e.g., influence + ongoing assessment + risk escalation), Description must capture the full scope rather than surfacing only the most visible sub-activity. Narrow Description framing hides the rest of the work and skews Impact framing toward the surfaced facet, which can also lead Impact prose into hindsight territory rather than at-the-time realized outcomes. Distinct from atomic decomposition: that rule fires when one entry bundles multiple separable activities that should split into multiple entries; this rule fires when one entry's activities genuinely belong together but the Description was authored too narrowly. 2026-05-07 reconciliation: EX-045 (LLX Solutions partnership work) Description originally captured only "identified and escalated obsolescence risk" and Impact leaned on hindsight ("partnership was subsequently ended"); rewritten to capture the full at-the-time activity (influence + ongoing assessment + gap communication) with Impact framing partial wins and surfaced gaps as the realized outcomes.
- **Leadership role coverage prompts.** For any leadership-tagged RL, builder prompts user for the dimensions that are commonly thin even when the role has moderate density: (a) people management of direct reports (size, role mix, accountability scope); (b) escalation handling; (c) sponsor/PI/cross-functional stakeholder communication; (d) approval and review work (regulatory documents, monitoring reports, study deliverables); (e) cross-region or cross-functional coordination. 2026-05-04 reconciliation: RL-011 (Regional CTM, 25 months) had 8 entries and was missing all five categories; user-prompted enumeration surfaced 9 additional atomic entries.
- **Sections 5 & 6 classified against axis vocabularies.** Tools (§5) and industry-exposure content (§6) classified against industry-pack and specialty-pack vocabularies for downstream retrieval. Tracked under deferral `inventory-builder-research-classification-sections-5-6`.
- **Pattern-of-work entries permitted as legitimate Description-only entries.** Some entries describe ad-hoc / pattern-of-work activity rather than a discrete deliverable (e.g., R-script foundation used across multiple investigation contexts; recurring consultative role across a portfolio). These are permitted with a Context line declaring the pattern (e.g., "Pattern-of-work entry; scripts written ad hoc to address emerging questions, not a prescribed activity"). Impact still desirable when realized outcomes exist; bare-tag Impact acceptable. Distinguish from missing-Impact defects: pattern-of-work entries are legitimate when explicitly framed in Context, while missing Impact on a discrete-deliverable entry is a defect. ## 6. Taxonomic Notes

- **People-leadership specialty scope is broader than direct-report management; bounded against operations-strategy.** Per `rules/specialties/people-leadership.md` capability vocabulary, the specialty covers vision-setting, strategic communication, cross-functional influence, change leadership, and stakeholder management beyond direct-report management. Tag substantiates when the capability vocabulary maps AND the work has people-management or change-leadership substance. **Boundary with operations-strategy:** pure organizational strategy or capability/technology strategy advisory work without people-management substance tags `operations-strategy`, not `people-leadership`. Both co-tag when the work spans both layers (e.g., org-design accompanied by hiring/managing the team that fills the structure). **Boundary application discipline:** PL/OS adjacency rule clarifies "operations-strategy carries the capability-and-structure design layer; people-leadership carries the people-management lens (managing the people in the structure)." When the entry's Description names only softer PL capabilities (cross-functional influence, strategic communication, stakeholder management) without explicit people-management activities (hiring, managing reports, change leadership of people, performance management), retag PL → OS.
